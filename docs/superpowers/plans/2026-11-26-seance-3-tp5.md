# TP5 — Filtre d'idempotence et recette de chaos

> Exécution : superpowers:executing-plans ; revue indépendante finale.

**Objectif :** réaliser les trois parties du TP5, pages 22–24, et les livrables de la page 25 du PDF complet fourni par l'utilisateur.
**Architecture :** CORE ajoute GET workflow_logs (Always Output Data) après la normalisation, puis If id vide. True poursuit le routage/PATCH/SUB via sélecteurs absolus ; False termine sur No Operation. SUB et OPS gardent leurs responsabilités.
**Stack :** n8n 2.42.7, Supabase/PostgREST, Bruno, Node.js, Git.

## Contraintes

- Conserver la clé déterministe existante `tickets:UUID:INSERT:nouveau`.
- Filtre séquentiel conforme au cours : ne pas annoncer un verrou atomique contre deux événements simultanés. Le verrou INSERT est une perspective d'architecture, hors topologie du TP.
- GET avec credential service_role, clé encodée dans l'URL, sortie vide propagée.
- PATCH : trois tentatives / délai 2000 ms / Stop Workflow, même sur HTTP 400.
- Poison pill : ne pas rejeter l'UUID dans le Code ; le rejet PostgreSQL doit être observé lors du PATCH.
- Déplacer les trois exports dans `orchestration/workflows/` ; mettre à jour les lecteurs de ces fichiers.
- Préserver la modification préexistante de `supabase/.gitignore` et tous les secrets.
- Les insertions, notifications et tests de crash sont ceux du TP demandé.
