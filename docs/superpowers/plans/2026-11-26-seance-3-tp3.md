**Goal:** Réaliser les pages 11–14 du support, la page 10 étant déjà réalisée.
**Architecture:** CORE normalise et met à jour le ticket puis appelle SUB de façon synchrone. SUB fait l'upsert d'audit et notifie si nécessaire.
**Tech Stack:** n8n 2.42.7, Supabase/PostgREST, Bruno, tests Node natifs.
**Spec:** PDF séance 3 pages 1–14 fourni dans Downloads, TP3 pages 13–14.

## Contraintes et contrat

- Conserver le webhook INSERT et le retry PATCH (3 tentatives, 2000 ms).
- Credential Supabase chiffré dans n8n, aucune valeur de secret dans Git.
- Entrées SUB : `idempotency_key`, `workflow_name`, `ticket_id`, `statut`,
  `alert_message` de type String ; `details` de type Object.
- `ticket_id` vide devient SQL NULL ; message vide signifie aucune notification.
- Retour compact `{ audit_saved: boolean, notification_sent: boolean }`.
- Audit en upsert sur `idempotency_key`, préférence merge-duplicates + representation.
- Les entrées du parent utilisent les sélecteurs absolus de Normalisation du ticket.
- Pas de TP4/TP5 : DLQ globale et filtrage des doublons avant traitement restent à faire.

## Review Focus

- Aucune notification directe ne subsiste dans CORE ; SUB est appelé sur les deux branches.
- Le message est lu depuis l'entrée du sous-workflow après la réponse HTTP d'audit.
- Une indisponibilité Discord rend `notification_sent=false` sans invalider l'audit.
- Une erreur d'audit ne doit jamais être annoncée comme un audit réussi.
- L'upsert empêche les doublons de ligne ; la déduplication de l'envoi des alertes n'est pas encore garantie.
